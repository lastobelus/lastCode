Who is watching
my pull request?

Two systems can wake your agent. One brings news. The other checks whether a particular version is ready.

Historical source snapshot inspected on 5 October 2026 at 8c62bda01e. The mockups below are proposals, not shipped controls.

Recommendation

Keep your Wait for PR action for delivery today.

It already understands your exact-commit CI and Codex-review rules and gives you a visible action run. For the longer term, use the built-in watcher as the app’s background notification system—but give it an obvious in-thread status card and keep the strict readiness checks before merge.

Don’t run both watchers for the same PR by default. That duplicates GitHub reads and can wake the agent twice for the same event. Neither needs Quick CI or local test builds merely to wait.

Imagine you’re baking a cake

Built-in PR watcher

A kitchen bell

“The timer rang!” “Someone left a note!” “There’s a problem!”

The bell is useful while you do other things. But a ringing bell doesn’t certify that the cake is ready to serve.

Wait for PR action

A checklist for this cake

“The right cake is baked, the inspection is done, and nothing changed while we checked.”

If you swap the cake—or the recipe changes—it stops and asks the agent to reassess. Even then, the agent must make the final serving decision.

What actually runs?

GitHub→Background observer→A message in this thread→Agent acts

Built-in: a service inside the running LastCode server checks watched PRs about once a minute. It saves what it has reported and queues new information behind an active agent turn. It is not an invisible AI thinking all the time.

Action: a managed script runs GitHub checks about once a minute, reports progress through Project Actions, then finishes with a structured reason. Action Resume brings that result back to this thread.

Both use network requests and some local processing. Both save model usage while idle; agent wake-ups still cost tokens. Neither is the heavy local Quick CI action.

Why watching can feel noisy—and invisible

In the 5 October 2026 motivating example, messages about old commits arrived after newer fixes were pushed. The native watcher queues reports behind an active turn. By delivery time, the branch may have advanced. Its rules also classify cancelled checks as failures and report newly failing checks incrementally.

The inspected code supports this explanation; this is not a complete trace of every queued event.

Make the mechanism visible. “Watching remains active” can sound like the visible Wait for PR action even when the built-in watcher was armed. Show its live state without requiring the reader to inspect tool calls.

Reconcile runtime guidance that selects the native watcher with repository skills that select Wait for PR. The intended policy remains an open design question.

What we would need to add

  1. A truthful live status. Active, paused because the thread is settled, unable to read GitHub, update queued, and stopped—with a reason. A saved watch flag alone must not mean “healthy.”
  2. Freshness and identity. Last successful read, current head, and what is still pending. The current watch schema has no last-successful-check timestamp, so this needs server data, not just a new badge.
  3. Less stale news. Re-check the revision before delivering queued check updates. Group cancellation fallout from superseded runs; preserve real failures and review findings. Never silently discard a review comment merely because its commit is old.
  4. One clear set of controls. Stop, restart, details and open PR. Show who armed the monitor and when it stops automatically. Keep equivalent status accessible on web, desktop and mobile.
  5. Keep the readiness gate. “Checks passed” should not say “ready to merge.” Preserve exact head/base/CI/review verification and the guarded merge. Resolve the contradictory agent guidance so it selects one waiting mechanism deliberately.

This document proposes watcher reconciliation; it does not implement it. Background browser QA and browser-disconnect follow-up are separate workstreams.

What I would use

Today: your Wait for PR resumable action for “babysit and merge.” Use the native watcher when the goal is simply “tell my agent about PR news.” Do not confuse either with merge authorization.

After the visibility work: make the native watcher the normal background experience, but reuse the strict readiness logic before it announces readiness or the agent attempts a merge. Don’t replace a precise gate with a prettier notification.

This dated explainer does not represent a live watcher status. Opening it does not arm a monitor or run local CI. Continue exploration and implementation in the same draft PR when requested.
