# Dopamine phase 3 · Should a dashboard tab follow the reader?

**Status:** Design investigation complete. The recommendation for the December 2, 2026 PT check-in is to keep phase 2 and defer automatic following. Implementation needs a separate decision.

[Dopamine phase 3](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/plans/dopamine.md#L222-L224) asks whether to keep a dashboard beside the reader when they switch LastCode threads. A loaded copy has a measurable cost. The available usage records establish that copies exist across threads, with too little information to tell whether they represent a repeated reader chore.

## How tabs work today

- **The right panel belongs to a thread.** [`rightPanelStore`](../apps/web/src/rightPanelStore.ts#L135) keeps surface order, selected surface and panel visibility under a scoped environment/thread key. [`openBrowser`](../apps/web/src/rightPanelStore.ts#L949) exposes a session as a panel surface. [The persisted store](../apps/web/src/rightPanelStore.ts#L1433) keeps the layout and recent browser selection order in client storage. A side chat can [host its surfaces in its parent's panel](../apps/web/src/components/chat/SideThreadPane.tsx#L49); its placement and the session's ownership are distinct.
- **The page is a separate resource.** [`PreviewManager.open`](../apps/server/src/preview/Manager.ts#L455) creates an environment-owned session keyed by thread ID and tab ID. [`previewStateStore`](../apps/web/src/previewStateStore.ts#L301) consumes its events and reconciles snapshots. On restart [the manager reads retained sessions](../apps/server/src/preview/Manager.ts#L247) from `preview-sessions.json`. It [drops native handles and back/forward state](../apps/server/src/preview/Manager.ts#L164) while retaining the current address, placement and other tab metadata. Desktop runtime IDs also include the environment and server epoch. [`previewRuntimeTabId`](../apps/web/src/browser/previewRuntimeTabId.ts#L4)
- **Hiding a panel and closing a tab have different costs.** [The panel toggle](../apps/web/src/components/chat/useRightPanelActions.ts#L178) changes visibility and can float the selected page. [`ElectronBrowserHost`](../apps/web/src/browser/ElectronBrowserHost.tsx#L379) mounts webviews on demand and keeps mounted guests while their sessions exist. A retained session can also be dormant and need reloading. [The tab-close handler](../apps/web/src/hooks/useRightPanelSurfaceClose.ts#L53) removes the surface and calls the authorized preview close; [`closePreviewSession`](../apps/web/src/components/preview/closePreviewSession.ts#L25) also records the tab for Reopen Closed Tab. Removing a surface alone cannot be used to reclaim its renderer.
- **Phase 2 is per thread.** [`openDashboards`](../apps/web/src/components/lastcodeDashboardsEntry.ts#L18) reads the project's Dashboards Action and opens its configured address using origin reuse. [`findReusablePreviewTab`](../apps/web/src/browser/lastcodePreviewTabReuse.ts#L97) selects the most recently selected successful same-origin tab for that entry, and [`reuseOpenPreviewTab`](../apps/web/src/browser/lastcodePreviewTabReuse.ts#L156) reveals it without navigating. Ordinary foreground links match the address, allowing a different query on loopback or `*.localhost` when origin, path and fragment agree. Reuse checks placement and excludes hidden, agent-owned and closing tabs. [In-page link handling](../apps/web/src/browser/ElectronBrowserHost.tsx#L149) excludes the source tab, so another query can open a sibling or reveal a different match. Cmd-click and middle-click open a new tab. Explicit agent opens and Action launch opens have their own entry points. [Dashboards entry and link reuse](https://github.com/lastobelus/lastCode/pull/852) · [Selection order](https://github.com/lastobelus/lastCode/pull/860) · [Source tab exclusion](https://github.com/lastobelus/lastCode/pull/861)
- **Following would be a new reader preference.** The current right-panel tab actions have no browser pin. Recent selection, a visible tab and a restored tab each mean something different from following. Dopamine's [manifest `pinned` field](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/src/model.ts#L282) [sorts](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/src/store.ts#L288) and [filters](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/web/hub.js#L123) the hub's list. A publisher can set it. Only an explicit reader action on a LastCode tab should start following.

## Evidence available at the check-in

### Loaded copies use memory

On November 27, 2026 PT, the installed macOS desktop was running LastCode checkpoint 5332. The experiment opened one desktop-hosted preview and three more at the same address, serially, in a background QA thread with the Incognito profile. It ran once for the hub index and once for a live dashboard shell. The hub index populated and each shell document finished loading with a dashboard frame address set. Renderer child PIDs and RSS were sampled with `ps` before opening, after the first tab loaded, and at four loaded tabs. New PIDs were attributed by their appearance during serial opens and disappearance on close. All ten baseline renderer PIDs stayed present. All QA tabs and added renderer processes were gone at the end.

| Page                              | First loaded tab, added renderer RSS | Four loaded tabs, added renderer RSS | Extra three copies at four tabs |
| --------------------------------- | -----------------------------------: | -----------------------------------: | ------------------------------: |
| Hub index                         |                        1 PID, 98 MiB |                4 PIDs, 459 MiB total |           3 PIDs, about 355 MiB |
| Dashboard shell and embedded page |                       1 PID, 119 MiB |                4 PIDs, 473 MiB total |           3 PIDs, about 356 MiB |

At the four-tab sample, the per-PID ranges were 104–119 MiB for the index and 117–119 MiB for the shell. The extra-copy column uses contemporaneous values for the three extra PIDs because the first process's RSS can drift. RSS includes shared pages, so the sums describe resident size and do not measure unique physical memory or the total app footprint. The OS count includes every additional renderer child seen in each run. There was no additional separately visible renderer PID per frame in this setup.

The experiment measures the cost of live copies using the installed Electron browser's [background desktop-root path](../apps/desktop/src/preview/BrowserRootWindow.ts#L8). It duplicates tabs in one scratch thread to isolate the copy count. Normal foreground opens can use the embedded webview path, other profiles can share processes differently, and retained sessions need no process while dormant. The result supports “each additional loaded copy can cost roughly a renderer and 120 MiB RSS on this setup.” It gives no resident estimate for the entire retained inventory or for switching threads in the foreground. A follow-up benchmark, if warranted, should stage the same open/close series across isolated threads using the normal foreground path and a single profile.

### Retained records show spread, without a reopen rate

Before the experiment, one environment's retained-session snapshot held 314 tabs. 26 were the hub index, a dashboard shell, or a direct dashboard origin, across 11 threads. Restricting the snapshot to rows whose last update is dated November 23–27, 2026 PT leaves 14 tabs in 10 threads. Six of those tabs, each in a different thread, were revealable and had no recorded automation owner. The index accounted for five distinct threads in that date range, and the most repeated individual shell for four. This counts surviving rows and their last update. It includes QA and automated activity and omits tabs already closed or removed. Even revealable, unowned tabs can have been opened by an agent for the reader. The inventory cannot distinguish an actual reopen from an initial open, reuse, restoration, navigation or an update to tab state.

- LastCode's [browser history](../apps/web/src/browserHistoryStore.ts#L79) upserts one latest visit per normalized address under a project key. The [thread-to-project mapping](../apps/web/src/browserHistoryStore.ts#L225) does not attach a thread or an open intent to each visit. It cannot recover overwritten visits or count manual reveals of already-open tabs.
- The retained desktop and server traces sampled on November 27 PT covered only part of the study window. Their browser spans did not carry matching dashboard addresses. [Renderer history](../apps/desktop/src/telemetry/DesktopRendererHistory.ts#L75) is a rotating incident log, without URL or reader intent, and truncates the runtime tab ID before a reliable join for long thread IDs. It did not identify live and dormant copies across the snapshot reliably. It remains useful for measuring process attribution when an experiment isolates the added PIDs.
- The hub's [request handler](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/src/hub.ts#L932-L1062) serves the index, shell and view reads without a per-open request history. The local hub log had no matching read entries. [Store revisions](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/src/store.ts#L301) and [action records](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/src/actions.ts#L104) describe data changes and button activity. Even a request count would mix browser windows, reloads, periodic reads and automation and would miss LastCode's in-place reveal.
- The source plan records some [reference-installation visits during phase 1](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/plans/dopamine.md#L106-L120). Those deliberate acceptance checks help explain the spread. They provide no daily usage rate.

There is no defensible estimate of reader reopens per thread for November 23–27 PT. The remaining days of the one-week observation can still supply a prospective sample.

## Options and behavior

| Option                                                     | Benefit and cost                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Rough implementation size                                                                                                                                                                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Close and reload on thread change**                      | The dashboard follows the active thread without leaving a loaded copy behind after each successful handoff. The page reloads for every new destination that needs a copy. Closing the surface and releasing the session are separate operations. Failure handling and window ownership make this more than a panel toggle.                                                                                                                                                                                            | Medium, roughly 2–4 engineering days for a desktop-only slice and targeted QA. A fork-owned thread-switch controller, tab menu entry, and small seams for selection, close and session open.                     |
| **One shared live tab**                                    | Switching threads can preserve scroll, disclosure, forms, back/forward and ongoing work. The current server, runtime IDs, ownership, IPC and view leases all bind the page to a thread. A movable surface would need its own durable owner and explicit rules for where new-window links, prompts and automation go.                                                                                                                                                                                                  | Large, roughly 1–2 engineering weeks for desktop scope and integrated proof. Changes span session, browser host, panel and transport contracts.                                                                  |
| **Keep per-thread tabs and make an explicit open cheaper** | Keep Phase 2. If starting from the index is the repeated friction, try an explicit **Open last dashboard** action scoped to the current desktop window and compatible hub. It opens the exact last address when needed, reuses an exact eligible tab in the destination, and leaves selection and page ownership local. It still creates copies. If memory is the only issue, first benchmark a bounded inactive-page discard policy for this class of tab; it preserves tab metadata and pays a reload on selection. | Zero for keeping Phase 2. About ½–1 engineering day plus QA for the explicit action. Discarding inactive pages is a separate browser lifecycle change and needs its own estimate after the foreground benchmark. |

If follow is eventually justified, start with **one explicitly followed tab per desktop window**, using close-and-reload on committed primary thread switches. A fork-owned module should call existing panel and preview commands. Keep a window-local record of the confirmed full URL, browser profile and desktop placement. Default to ending follow on window close. Follow records should use a separate reader preference from the hub manifest and from tab reuse rankings.

- **Ownership and splits.** Multiple windows can show the same thread and share server sessions. A window must never close a tab presented elsewhere or adopted from another thread's normal tabs. A side-chat pane is hosted in the parent panel; focus inside it should cause no transfer. Use authoritative window-local ownership and presentation facts for automatic cleanup. If that authority is unavailable, skip transfer while a second presenter or split panel is active. Switching the owning window may close only a session it created for follow, and only once other presenters have released it.
- **Destination and ordering.** Allow same-desktop transitions to projects that configure the identical viewing origin. For linked environments, verify the resolved browser host is the same desktop, the same profile is available, and the destination has preview read and operate scopes. `*.localhost` resolves on the browsing host, so an environment-hosted session could reach a different hub. Skip unsupported or disconnected destinations with follow paused. Keep the destination's selected surface or closed panel when it was explicitly chosen during a switch. When safe, prepare a destination session without stealing focus, then retire the owned source after the destination is ready. Use the latest committed switch and panel revision to guard against late results; discard only superseded sessions created for follow. A brief two-copy overlap is preferable to losing the source on failed opens. A borrowed destination tab stays the thread's tab when follow moves on.
- **Intentional dismissal.** Closing the followed tab, including via keyboard or bulk close, ends following for that window. Hiding the panel pauses automatic presentation until the reader shows it again. Automatic retirement should call the existing close command and use session reconciliation, without producing user-close history entries on every switch. **Stop following** leaves the current tab open as an ordinary thread tab. No automatic reopen after a deliberate close.
- **Deleted or unavailable pages.** Dopamine's [shell lookup](https://github.com/lastobelus/dopamine/blob/d001e671d5c925a52e79c4e6e55fae1b832a754b/src/hub.ts#L941-L963) can show an unavailable dashboard inside a successful HTML response. Preserve the current location and let the reader stop or pick another tab; treat a timeout as unavailable and allow retry through the hub's existing screen.
- **Page state and reuse.** Carry the exact URL including query and fragment, stripped of any ephemeral preview credential. A reload keeps only state the site and profile already persist. Scroll, unsaved inputs, in-memory disclosures, and back/forward history can be lost. Match an existing destination only on exact full address plus compatible profile, runtime and host, with the normal owner and visibility exclusions. The looser Phase 2 origin and loopback-query matches still govern ordinary opens, and the source-tab exclusion and Cmd-click behavior still apply. If retaining live browser state turns out to be the main goal, reconsider the shared tab with that use case in hand.

## Decision and smallest additional measurement

**Keep phase 2 for now.** The memory result is large enough to track if loaded copies build up, but a close-and-reload feature imposes new churn on every eligible thread switch. The retained inventory does not justify that exchange. At the check-in, ask whether looking up the same dashboard after switching is a daily interruption. An explicit last-dashboard action is the smallest candidate if the repeated step is finding the same page; reconsider auto-follow only if the reader wants it to stay visible across switches and accepts reloads.

Use a short local tally for the rest of the week. Across normal primary-thread switches, note whether the reader wanted the same dashboard again and whether that meant revealing an existing tab, creating a tab, or doing nothing. As a proposed decision threshold, reconsider automatic follow if that step interrupts the reader at least twice per active day on three separate days and a foreground measurement shows multiple live copies repeatedly. Confirm the threshold at the check-in.

If a manual tally is insufficient, a separate change could add a **seven-day, opt-in, local-only diagnostic** at two client seams: committed primary-thread switches and explicit foreground dashboard opens. Reuse the configured hub origin and browser placement checks. Count eligible switches, same-dashboard attempts after a switch, warm reveals, new sessions and failures. Count attempts using a short post-switch window and one event per explicit action. Include only a coarse day and an installation-local keyed digest of the scoped thread and exact dashboard identity if per-thread totals are needed. Exclude tool and Action opens, automatic restores, redirects, reloads and polling. Keep the records bounded, expire them after seven days and export counts only. This yields a denominator and the distribution across threads without collecting raw URLs, queries, thread IDs, page content or credentials.
