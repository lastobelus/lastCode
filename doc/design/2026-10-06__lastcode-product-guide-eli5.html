A scheduled task is a recurring message to an agent.

At the time you choose, LastCode sends a saved prompt to an agent, which does the work in a thread. The environment that owns the task must be running. Your browser can be closed.

Use it when the job needs judgment, such as “Read this week's changes and suggest what needs attention.” Exact commands and always-on services have better homes; see the table below.

Choose the right kind of automation

Tool Good example Why it fits
Scheduled task Summarize new issues every weekday. The result needs reading, reasoning or prioritizing. Uses model quota.
Project Action Run an exact test command, Quick CI, a package build, or wait for a PR. A saved command does predictable work. An opted-in Action can send its result back to the same agent when it finishes.
OS service or timer Keep LastCode or a database running; perform a staged app update. It must keep working while LastCode is stopped, starting or being replaced.

Set one up

  1. Open Settings → Scheduled tasks. Select the environment and project that own the work.
  2. Choose New task, then a prompt, model, workspace and permission mode. Say clearly what the output should be and what the agent must not do.
  3. Choose At a time, an interval, or On webhook. Fixed times use the environment's time zone, which may differ from your laptop's or phone's. The shortest interval is one minute.
  4. Save. From the list you can edit, pause, resume, run now or delete. Webhook tasks run when a request arrives, so they have no Run now. Tasks bound to a thread also appear in that thread's automations panel.

Where the results go

  • A new thread for each run — the default in the settings form. Good for independent reports, such as a daily summary.
  • An existing thread — the default for tasks an agent creates (they bind to the calling thread). Good for a continuing investigation. The prompt waits behind work already running there; it does not interrupt a tool.
A good first prompt

“Review new issues since your last report. Give me the three most useful decisions, with links and reasons. Do not change files, contact anyone, or close issues.” Start daily or weekly, and adjust after reading a few results.

What the clock does and does not promise

  • After downtime, an overdue interval task runs once to catch up. It does not replay every missed run.
  • A fixed-time run that is more than ten minutes late is skipped until its next slot.
  • “Succeeded” means the prompt was dispatched, not that the agent finished the work successfully. Read the thread for the real outcome.
  • A frequent schedule can queue work faster than the agent finishes it.

A webhook can react to events such as a CI failure or a new PR. A public webhook URL uses T3 Connect; request signatures and optional offline holding are separate settings. Read the existing webhook guide before connecting an outside sender.

Recommendation: keep whatever runs or updates LastCode outside LastCode. Move an existing timer into a scheduled task only if its real job is to ask an agent for judgment and it already depends on LastCode being online. For scripts that do the same thing every time, keep their OS timer or use an Action; an agent should not be paid to act as a clock. Your actual inventory and candidates are in the private companion.

Snooze hides the wait. Auto-resume continues the work.

Limited means the provider stopped the turn because a usage or rate limit was reached. That is different from an agent waiting for your answer or approval, or a tool that broke.

When the provider reports a valid reset time, LastCode can hide the thread until then, send “Continue where you left off.” at the reset, or both. Both are off by default.
Auto-resume Snooze What happens at the reset
Off Off The thread stays visible. You decide when to resume.
Off On The thread reappears. No prompt is sent.
On Off The thread stays visible and is told to continue.
On On The thread reappears and is told to continue.

Try the two switches (illustration only):

Visible while waiting. At reset: waits for you.

Set the defaults

On web or desktop, open Settings → General and find Auto-resume limited threads and Snooze limited threads. On mobile, use Settings → Thread behavior. These belong to an environment, so select the right one first. Projects cannot override them.

Choose for one thread

  • In a limited thread, choose Resume at reset or Snooze until reset for that stop.
  • Cancel auto-resume removes the continuation. Wake now removes the snooze. They are independent: waking early does not cancel auto-resume, and canceling auto-resume does not wake a snoozed thread.
  • Changing a default does not undo choices already saved on a thread. Undo those in the thread itself.
  • To continue by hand, use Resume in an empty composer.

When auto-resume can work

  • The most recent turn stopped on a usage limit LastCode recognizes, and the reset time is later than that stop. Without a reset time, you retry by hand or use an ordinary snooze.
  • The owning environment is running. Saved choices survive a restart, and an overdue continuation can run when the server comes back. Timing follows the server's scheduler, not an exact alarm on your phone.
  • Nothing has changed the situation. A new turn, a different provider, archiving, deleting, settling, or a pending approval or question can prevent the continuation from starting. A longer manual snooze delays it.
  • Queued messages stay saved. The limited turn continues first, and the queue follows once the continuation finishes. A queue that was held separately may still need a manual resume.

Today only the Codex and Claude adapters add reset times to limit stops, when available; the other adapters checked do not. Even then, the allowance may not actually be usable at that moment. LastCode never guesses a reset time and never switches providers for you.

Example

A research turn hits its weekly limit at 10:00, with a reset reported for 14:00. Snooze keeps your inbox quieter for four hours. Auto-resume asks the agent to continue around 14:00. Turn on both to get both. Neither one answers a question the agent was waiting on.

Recommendation: turn on both for work you are happy to let continue unattended. Use snooze alone when you want to rethink cost or direction before restarting. For one important thread, keep it visible and choose Resume at reset yourself.

Keep the research. Reclaim what you can reinstall.

A worktree is another checkout of your project. One worktree can hold irreplaceable notes and replaceable dependency installs side by side. Deleting the whole checkout and deleting only its dependencies are very different decisions.

Automatic and explicit deletion are not equally careful.
  • Automatic whole-worktree cleanup first checks for local work and for anything still using the worktree.
  • Explicit worktree deletion currently force-removes the checkout, without those Git and ignored-file checks.
A confirmation dialog is not a backup of your research.

What the current storage switches do

Setting in Settings → Storage What it removes Keep in mind
Delete worktrees with deleted threads A managed worktree after its last thread is deleted. The automatic safety checks still apply. Deleting a thread does not mean force-deleting its files.
Delete unchanged worktrees Managed worktrees with no commits beyond the default branch. The safety checks for local files still apply. “Unchanged” does not mean “unimportant.”
Delete inactive worktrees Managed worktrees after the number of inactive days you choose. Branches and conversations stay. Being inactive does not make research disposable.
Delete merged worktrees A worktree whose PR is merged and whose commits are in the default branch. Squash merges can fail that commit-history check, so the checkout stays.
Delete old browser artifacts Saved captures in the environment's browser-artifact folder, by age. Old capture links stop working. Browser profiles, message attachments and other copies of desktop captures are not touched.
Delete old rotated logs Old rotated log files. Current logs are kept. This is not a general log-folder cleanup.
  • Every rule is off by default.
  • Cleanup runs at startup, after a setting changes, and every hour.
  • Worktree rules can be Inherit, Off or Custom for each project or checkout. Browser and log retention apply to the whole environment.
  • Choosing All environments changes connected servers only, not offline ones.

Does an ignored tmp/ folder protect my work?

Yes, from automatic whole-worktree cleanup — if tmp/ really is ignored there.

  • The only ignored folder automatic cleanup will delete is node_modules/. Any other ignored content, such as research in tmp/, blocks removal. Tracked changes and untracked files block it too.
  • Whether tmp/ is ignored depends on the checkout. The current repository's root ignore file does not ignore it. Older worktrees, local exclude rules and your global ignore file may. Check the real rules instead of trusting the folder name.
  • None of this protects against explicit deletion, which force-removes the checkout.

Automatic removal is also blocked by active or queued work, live provider sessions, terminals, preview leases, shared worktrees and project roots. If many worktrees are kept, the safeguards may be working as intended.

A separate, unmerged change implements that narrower rule: proposed only, off by default. It targets only ignored npm/pnpm root node_modules installs that it positively recognizes. It is not a switch in the version checked here. Build output, vendored source, tmp/ and research are outside its initial scope. Treat its final controls and guarantees as unconfirmed until it ships.

Broader cleanup for archived work and older unarchived checkouts is a separate proposal for a new PR. It would cover positively recognized build outputs and installed dependencies across stacks, while preserving reference source, local state, research and retained release files. That proposal does not expand or block the narrower change.

Screenshot settings will not save much disk

Settings → SnapShots controls desktop capture, app text, the shortcut, sound, flash and animation. There is no format, quality or maximum-size setting for screenshots. Captures start as PNG, and oversized attachments are compressed automatically. Turning off app text avoids some extra data, but it will not fix a large dependency folder. Browser-artifact retention does not remove attached screenshots.

Recommendation: keep the broad inactive and merged rules off while uncommitted research matters. Keep sensible browser and log retention, and save lasting evidence somewhere that does not expire. For space, measure build output and installed dependencies, including hidden folders, before ranking cleanup targets. Reclaim only recognized, inactive files in a separately approved cleanup. Folder names alone are not permission to delete.

The project Dashboard shows what needs your attention.

LastCode built it. In LastCode's history, “Open dashboard” comes from LastCode's live-project-dashboard contribution. The upstream branch we checked has neither the route nor the menu entry, so there is no upstream dashboard to rebuild our reports on.

How to open it

  • A project's context menu → Open dashboard, or the dashboard icon in the project heading.
  • The command palette → Open project dashboard.
  • A thread's context menu, which opens that thread's project dashboard.

All of these open the same view.

Needs your attention

Questions, approvals, input requests, plans and failures you can act on.

Work in motion

Threads that are working right now.

Progress & updates

Progress and results reported by agents.

Parked contexts

Threads set aside for later.

It shows one project on one environment. The sidebar can group matching projects from several machines, but the dashboard does not combine their work. Subagents, archived threads and deleted threads are left out. The mobile app has no equivalent dashboard in the checked code.

Where the other status views are

What you want Where to go What it answers
Project attention Project → Open dashboard Which conversations need me?
Checkpoint history Run lastcode-checkpoints in a terminal; add -n 20 or --verbose. Which checkpoints and revisions exist?
CI or package runs Run the relevant Project Action; open its terminal for details. Did this command finish, and if not, why?
Local nightly or build progress Settings → LastCode → Show and install local nightlies; also the sidebar updater. Which version or build is available or in progress?
A saved HTML report Open its file link; choose Open file in preview browser if needed. What did the report say when it was written?

The repository has no separate shipped HTML dashboard for CI, builds or nightlies. You may have a personally saved report elsewhere, but it can't be identified here without its file or link. The checkpoint terminal view and the updater are confirmed features.

Should these share code?

They look alike — status, progress, links, actions — but their data comes from different places. Thread questions come from conversation state. Package progress comes from build state. Checkpoint history comes from tags and records. A saved HTML report may be a fixed snapshot.

Recommendation: start by adding links to the existing status views, and use the existing file preview for saved HTML. If two live views really show the same status, share that one small data helper or component. Nothing here justifies a shared dashboard framework or a broad refactor.

An environment is the place that owns the work.

It holds the running server, the files, provider credentials and conversation history. A laptop, a remote workstation and a build server can each be a separate environment. Your phone or browser is only the control panel: opening it there does not move the work onto that device.

Routes are different doors into the same place

Route Use it when What stays the same
This device / loopback The server is on this desktop. The environment, its files and its conversations. Adding a route does not copy or move them.
LAN Both devices are on the same reachable network.
Tailscale Both devices can use the same private tailnet.
T3 Connect You want managed remote access without router port forwarding.
Public URL / SSH You already have a reachable server URL, or desktop can set up an SSH-forwarded connection.
  • Tunnel means the remote-access path through T3 Connect. Relay means the go-between that carries that connection. Neither is a second environment.
  • A direct connection uses the server's own address. SSH is a different, forwarded path with its own setup.

Manage routes in Settings → Connections on web or desktop, and Settings → Environments on mobile. A saved machine can have several routes. LastCode tries them in order, falls back when one fails, and can return to an earlier route once it works again. Pairing the same machine at another address adds a route, not another machine. The hosted HTTPS web client needs a secure route the browser can reach.

A device hub connects test devices

Open Settings → Integrations → Devices. The environment's device hub finds simulators and emulators and streams them. By default they run beside its server. Under Device hosts, an SSH-connected machine can supply devices without owning your project or agent.

Example: Linux work, iOS testing

Your source and agent live on managed-server. An iOS simulator lives on a Mac called device-host. Add that Mac as an SSH device host to the Linux environment, and keep the Linux environment selected for agent work. Pick the Mac as the environment instead only if the project and provider themselves should run there.

  • SSH aliases and keys are looked up on the owning environment's server.
  • Test connection checks for tools without installing anything. The first device listing installs the pinned device tools.
  • Builds, app installs and a reachable development server still need setting up. A remote simulator cannot use another machine's localhost without a reachable address or port forwarding.

Can a child thread live somewhere else?

No. Grouped child threads and delegated subagents stay in their parent's environment. A child is grouped under its creator only when its environment and project match the parent's. The current create-threads operation makes threads in the caller's own project. Work on another machine is a separate thread owned by that environment, not a child that crosses environments.

The sidebar can group matching repositories from several environments. That changes what you see together, not who owns each thread. Auto balance can pick an environment for a new thread; existing threads stay where they started. On mobile you pick the environment yourself.

Why an agent may not open a thread ID from another environment

Your client can connect to several environments, but the agent's thread-read and thread-send tools only look in their own environment. They take a thread ID with no way to name an environment or route, so a bare ID from elsewhere is not enough. Instead, open that environment in the client and ask an agent there, or paste the relevant text into this conversation. Cross-environment links do not yet work with these tools.

A naming trap: a thread's Local workspace means the project's current checkout rather than a new worktree. It does not mean “on the device I am looking at.” Desktop's Local environment setting, by contrast, really is about the server on that desktop.

Recommendation: choose the environment by where the files, tools and credentials should live. Choose routes by how reliably you can reach it. Add a device host only when testing needs another machine's simulator or emulator.

A profile keeps a login. A capture keeps evidence.

The built-in Browser panel can sign in as different identities, capture a page, or record a short walkthrough. Desktop SnapShots capture another app into your draft. The names sound alike, but the jobs differ.

The short version: a profile is a reusable browser identity. A screenshot shows one moment. A recording shows what changed. An agent snapshot also describes the page's controls. None of these is a Git checkpoint.

Browser profiles: separate accounts without signing out

Go to Settings → Integrations → Browser profiles → Add profile → Blank profile. Make one called Work and one called Personal, then pick a profile when you open a Browser tab. A tab keeps its profile for life; changing the default only affects new tabs.

  • Logins are shared per device, environment and profile. Tabs using the same profile on the same desktop and environment share cookies, logins and site storage. Another desktop or another environment has separate login data, even with the same profile name.
  • Default and custom profiles survive a restart. Incognito lasts until the desktop app process quits; closing one tab does not clear it.
  • You can create up to 24 custom profiles, with names up to 48 characters. Default and Incognito cannot be renamed or removed.
  • Clear cookies and cache also clears site storage, IndexedDB and service workers, so expect to sign in again. Remove profile and data deletes that profile's data across the environments it knows about, where possible.
  • Importing cookies copies them once. It does not keep syncing logins from another browser.

Pick the right kind of evidence

Capture How to make it Where it goes
Browser screenshot Click the camera button in the Browser panel. A local PNG. The toast offers Copy image, Copy path and Reveal. It is not attached to the composer automatically.
Browser recording Shift-click the camera to start; click again to stop. A local video, with Reveal and Copy path. Attach it yourself if you want it in a conversation.
Agent preview snapshot An agent calls preview_snapshot. Page text, controls, diagnostics and an image, returned to the agent. A saved PNG path needs save: true.
Desktop SnapShot Turn on Settings → SnapShots, then press the capture shortcut with another window in front. The image, and optionally the app's text, attach to your draft. Nothing is sent automatically.
Git checkpoint LastCode records it so you can diff and restore. A hidden Git reference to file and staging state. No image or video.

Recordings: keep them short

  • A recording captures the preview browser tab only, with no audio.
  • Settings → Integrations → Browser sets a maximum frame rate of 30 fps (the default) or 60 fps, and optional key and mouse overlays. Password fields never appear in the key overlay. Changes apply to new recordings.
  • The format is picked automatically: MP4 (H.264) when supported, otherwise WebM. Resolution follows the tab. There is no quality setting.
  • There is no fixed length limit, but agents can only transfer recordings up to 50 MiB. A short reproduction is easier to share than a long session.

Desktop SnapShots: show the agent what you see

  • Off by default. Available on macOS, Windows and Linux Wayland; X11 is not supported.
  • The default shortcut on macOS and Windows is both Shift keys together. On Linux, setup depends on the desktop.
  • macOS needs Screen Recording permission, plus Accessibility when Include app text is on.
  • The target draft is fixed when the capture starts, even if focus moves. With no thread open, the capture starts a draft in the current project. Captures not yet saved to a draft survive an app restart.
  • Sound, flash and animation only change the feedback, not the saved image.

There are no format, quality or size controls. Captures start as PNG. Images within the 10 MiB attachment limit are kept as they are. Larger ones are automatically shrunk and compressed to WebP or JPEG, with the longest edge at most 2048 pixels. Anything over 50 MiB is rejected.

Agent snapshots

An agent snapshot helps the agent find buttons and understand the page, not just see pixels. Its image is at most 1280 pixels wide; text is capped near 20 KB, and the snapshot says what was left out. includeImage: false asks for text only; save: true saves a PNG; using both returns the saved path or URL without the full page description.

Which apps can do this

Browser profiles, the camera and recording are provided by the desktop app. Web and mobile can control an agent whose environment has a connected desktop browser host, but they do not provide Electron capture themselves. Without such a host, the agent's browser tools are unavailable.

What retention deletes

Browser-artifact retention deletes expiring captures in its environment's artifact folder. It does not erase browser profiles, attached screenshots, recordings copied elsewhere, or Git checkpoints. A saved screenshot path and a conversation attachment last for different lengths of time.

Recommendation: use persistent Work and Personal profiles for accounts, and Incognito for temporary tests. Use a screenshot for a layout problem and a short 30 fps recording for a sequence of steps. Use a SnapShot when the problem is in another desktop app. Before capture retention expires, keep lasting evidence as a deliberate attachment or saved file.
