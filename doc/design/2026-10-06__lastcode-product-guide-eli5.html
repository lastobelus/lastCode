A scheduled task sends a saved message to an agent.

At the time you choose, LastCode sends a saved prompt to an agent, which does the work in a thread. The environment that owns the task must be running. Your browser can be closed.

Use it when the job needs judgment, such as “Read this week's changes and suggest what needs attention.” Exact commands and always-on services have better homes; see the table below.

Choose the right kind of automation

Tool Good example Why it fits
Scheduled task Summarize new issues every weekday. The result needs reading, reasoning or prioritizing. Uses model quota.
Project Action Run an exact test command, Quick CI, a package build, or wait for a PR. A saved command does predictable work. An Action opted in with Allow Codex and Claude to run and resume sends its result back to the same agent when it finishes.
OS service or timer Keep LastCode or a database running; perform a staged app update. It must keep working while LastCode is stopped, starting or being replaced.

Set one up

  1. Open Settings → Scheduled tasks. Select the environment and project that own the work.
  2. Choose New task. Write the prompt, pick a model, and pick a workspace: Create a new worktree, Use the project checkout or Use a specific checkout. Say clearly what the output should be and what the agent must not do — the form has no permission-mode choice, and new tasks run with full access.
  3. Choose At a time, Every interval or On webhook. Fixed times use the environment's time zone, which may differ from your laptop's or phone's. The shortest interval is one minute.
  4. Choose Create task. From the list you can edit, pause, resume, run now or delete. Webhook tasks run when a request arrives, so they have no Run now. Tasks bound to a thread also appear in that thread's automations panel.

Where the results go

  • A new thread for each run — the default in the settings form. Good for independent reports, such as a daily summary.
  • An existing thread — the default for tasks an agent creates (they bind to the calling thread). Good for a continuing investigation. The prompt is queued behind work already running there; it does not interrupt a tool. It uses that thread's current provider and model; the task's saved model is only for new threads.
A good first prompt

“Review new issues since your last report. Give me the three most useful decisions, with links and reasons. Do not change files, contact anyone, or close issues.” Start daily or weekly, and adjust after reading a few results.

What the clock does and does not promise

  • After downtime, an overdue interval task runs once to catch up. It does not replay every missed run.
  • A fixed-time run that is more than ten minutes late is skipped until its next slot.
  • “Succeeded” means the prompt was dispatched, not that the agent finished the work successfully. Read the thread for the real outcome.
  • A frequent schedule can queue work faster than the agent finishes it.
  • While its environment is paused, no task wakes up. After you resume, each schedule applies the catch-up rules above.

A webhook can react to events such as a CI failure or a new PR. A public webhook URL uses T3 Connect. Filters, Replay key, Coalesce key, Require signature and Skip requests older than decide which requests reach the agent, and Deliveries shows what arrived. To keep requests while LastCode is offline, use Settings → Sharing & access → Hold webhooks while offline. These shape what the agent receives; they do not turn the task into a fixed command. Read the webhook guide before connecting an outside sender.

Recommendation: keep whatever runs or updates LastCode outside LastCode. Move an existing timer into a scheduled task only if its real job is to ask an agent for judgment and it already depends on LastCode being online. For scripts that do the same thing every time, keep their OS timer or use an Action; an agent should not be paid to act as a clock. Your actual inventory and candidates are in the private companion.

Snooze hides the wait. Auto-resume continues the work.

Limited means the provider stopped the turn because a usage or rate limit was reached. That is different from an agent waiting for your answer or approval, or a tool that broke.

When the provider reports a valid reset time, LastCode can hide the thread until then, send “Continue where you left off.” at the reset, or both. Both are off by default.
Auto-resume Snooze What happens at the reset
Off Off The thread stays visible. You decide when to resume.
Off On The thread reappears. No prompt is sent.
On Off The thread stays visible and is told to continue.
On On The thread reappears and is told to continue.

Try the two switches (illustration only):

Visible while waiting. At reset: waits for you.

Set the defaults

Open Settings → Threads → Usage limits on web, desktop or mobile. Resume after usage limits is auto-resume; Snooze until limits reset is snooze. These belong to an environment, so select the right one first. Projects cannot override them.

Choose for one thread

  • In a limited thread, choose Resume at reset or Snooze until reset for that stop.
  • Cancel auto-resume removes the continuation. Wake now removes the snooze. They are independent: waking early does not cancel auto-resume, and canceling auto-resume does not wake a snoozed thread.
  • Changing a default does not undo choices already saved on a thread. Undo those in the thread itself.
  • To continue by hand, use Resume in an empty composer.

When auto-resume can work

  • The most recent turn stopped on a usage limit LastCode recognizes, and the reset time is later than that stop. Without a reset time, you retry by hand or use an ordinary snooze.
  • The owning environment is running. Saved choices survive a restart, and an overdue continuation can run when the server comes back. Timing follows the server's scheduler, not an exact alarm on your phone.
  • The environment is not paused. A paused environment wakes nothing, even after a restart or reconnect, until you choose Resume. Reaching the reset time does not override your pause.
  • Nothing has changed the situation. A new turn, a different provider, archiving, deleting, settling, or a pending approval or question can prevent the continuation from starting. A longer manual snooze delays it.
  • Queued messages stay saved. The limited turn continues first, and the queue follows once the continuation finishes. A queue that was held separately may still need a manual resume.

Codex, Claude and Muse can report a reset time for limits they recognize, when one is available. Not every provider or limit has one. Even with a reset time, the provider may not accept the next turn at that moment. LastCode never guesses a reset time and never switches providers for you.

Example

A research turn hits its weekly limit, with a reset reported four hours away. Snooze keeps your inbox quieter until then. Auto-resume asks the agent to continue when the reset arrives. Turn on both to get both. Neither one answers a question the agent was waiting on.

Recommendation: turn on both for work you are happy to let continue unattended. Use snooze alone when you want to rethink cost or direction before restarting. For one important thread, keep it visible and choose Resume at reset yourself.

Keep the research. Reclaim what you can reinstall.

A worktree is another checkout of your project. One worktree can hold irreplaceable notes next to dependency installs and build output you can recreate. LastCode has three separate tools for it, from gentlest to strongest.

Tool What goes What stays
1 · Remove generated files Recognized dependency installs and unchanged build output. The checkout, your source, notes and anything else you added.
2 · Suspend the worktree The checkout folder, after its local work is saved. A saved copy you can restore by continuing the thread.
3 · Delete the worktree The whole checkout, permanently. The branch and the conversation. Nothing else is saved for you.

Automatic rules and deleting a worktree yourself are not equally careful.
  • Automatic rules check for local work and for anything still using the worktree first.
  • Deleting a worktree yourself force-removes the checkout and can lose local work. It only stops for Keep workspace, a saved copy, another owner, the project root or an open preview.
A confirmation dialog is not a backup of your research.

1 · Remove generated files, keep the checkout

In Settings → Worktrees → Dependencies and verified builds, turn on Remove inactive dependencies and build outputs. It reclaims npm and pnpm installs and build files that LastCode's build tools recorded and that have not changed since.

  • Build folders it recognizes today: apps/<app>/dist and native/resource-monitor/target/debug. It leaves other caches, vendor folders, other Cargo targets and other stacks' dependencies alone.
  • The delay counts from when the dependencies or build output were last really used, not from chat activity or folder dates. Archived threads qualify straight away.
  • An install shared by several threads stays until every one of them is archived with cleanup on.
  • Reinstall or rebuild before you continue work in that checkout.
  • Build output from before LastCode recorded it stays protected. Use Settings → Worktrees → Review older builds to approve exact files. Saving approves; it does not delete or turn cleanup on. New, changed and unselected files stay. Each review covers up to 1,000 files and 512 MiB per build folder.

2 · Suspend a settled worktree

Suspend settled worktrees, also under Settings → Worktrees, saves the checkout's local work — staged and unstaged changes plus supported local and ignored files — and then removes the checkout. The conversation stays where it is. Continue the thread and the saved copy is restored first.

  • Automatic suspension stays off until you set Suspend after, pick which threads may suspend (Finished subagents, Child threads you haven’t joined, Top-level threads and threads you’ve joined) and choose Save suspension policy.
  • To do it by hand, use Suspend worktree and Restore worktree. A manual restore also turns on Keep workspace; turn that off yourself when normal rules should apply again.
  • Saved copies never expire on their own. Open Manage saved workspaces to restore or discard them. They live on this machine: local recovery, not a backup.
  • Active work, and workspaces it cannot save, are kept as they are.

3 · Delete a worktree permanently

Setting under Permanent deletion What it removes Keep in mind
Delete worktrees with deleted threads A managed worktree after its last thread is deleted. The automatic checks still apply. Deleting a thread does not force-delete its files.
Delete merged worktrees A worktree whose pull request merged into the default branch. Squash and rebase merges count if the checkout is still exactly at the pull request's last commit.
Delete inactive worktrees Worktrees inactive for the number of days you choose. Clean archived checkouts qualify straight away. Inactive does not mean disposable.
Delete settled worktrees A worktree after its thread settles. 0 days means at the next cleanup after settling.
Delete unchanged worktrees Worktrees with no commits beyond the default branch. “Unchanged” does not mean “unimportant.”

Automatic deletion always keeps a checkout that has edits, untracked files or unknown ignored files; settings show this as Local work is preserved. Generated files are reclaimed separately first, so a leftover node_modules alone no longer decides anything. Other ignored contents still block deletion (an ordinary .DS_Store does not).

Rules shared by all three

  • Every rule is off by default.
  • Automatic cleanup runs at startup, after a setting changes, and every hour.
  • Each project or checkout can Inherit, turn rules Off, or use Custom rules. Off stops automatic cleanup and suspension for that project.
  • Keep workspace protects one checkout from all three automatic tools.
  • Running agents, sessions, terminals, previews, processes and project roots block automatic removal. If many worktrees are kept, the safeguards may be working as intended.
  • Choosing All environments changes connected servers only, not offline ones.

Does an ignored tmp/ folder protect my work?

  • From automatic deletion: yes, if tmp/ really is ignored there.
  • From suspension: not by keeping the folder. Supported notes are saved with the rest of the local work and come back when you restore.
  • From deleting the worktree yourself: no. That force-removes it.
  • Whether tmp/ is ignored depends on the checkout. The current repository's root ignore file does not ignore it. Older worktrees, local exclude rules and your global ignore file may. Check the real rules instead of trusting the folder name.

Captures and logs

Settings → Maintenance holds Delete old browser artifacts and Delete old rotated logs. These apply to the whole environment. Old capture links stop working; browser profiles, message attachments and other copies of captures are not touched, and current logs are kept. Delete now runs your enabled rules immediately, with their usual safeguards; it is not the same as deleting a worktree yourself. On mobile, all cleanup settings, including the worktree rules, are under Settings → Maintenance.

Screenshot settings will not save much disk

Settings → SnapShots controls desktop capture, app text, the shortcut, sound, flash and animation. There is no format, quality or maximum-size setting for screenshots. Captures start as PNG, and attachments are resized and compressed automatically. Turning off app text avoids some extra data, but it will not fix a large dependency folder.

Recommendation: start with generated-file cleanup; it is the least risky way to win back space you can reinstall. Use suspension for settled work you might return to. Keep the broad inactive and merged deletion rules off while uncommitted research matters. Keep sensible capture and log retention, and save lasting evidence somewhere that does not expire. Folder names alone are not permission to delete.

The project Dashboard shows what needs your attention.

LastCode built it. This checkpoint records the live project Dashboard as a LastCode contribution. It is the app's view of project activity; a saved HTML report or a build-progress screen answers a different question.

How to open it

  • A project's context menu → Open dashboard, or the dashboard icon in the project heading.
  • The command palette → Open project dashboard.
  • A thread's context menu, which opens that thread's project dashboard.

All of these open the same view.

Needs your attention

Questions, approvals, input requests, plans and failures you can act on.

Work in motion

Threads that are working right now.

Progress & updates

Progress and results reported by agents.

Parked contexts

Threads set aside for later.

It shows one project on one environment. The sidebar can group matching projects from several machines, but the dashboard does not combine their work. Archived and deleted threads and subagents still owned by another thread are left out. An independent thread can appear even if it began as a subagent. The native mobile app has no equivalent dashboard in this checkpoint.

Use Dashboard project to switch projects. Attention filters such as Quick, Focused, Computer and On my phone help you choose what to handle next. The phone filter does not add a native mobile dashboard. Check the connection label: Live means current data; a disconnected dashboard shows the last known state.

The repository has no separate shipped HTML dashboard for CI, builds or nightlies. You may have a personally saved report elsewhere, but it can't be identified here without its file or link. The checkpoint terminal view and the updater are confirmed features.

Should these share code?

They look alike — status, progress, links, actions — but their data comes from different places. Thread questions come from conversation state. Package progress comes from build state. Checkpoint history comes from tags and records. A saved HTML report may be a fixed snapshot.

Recommendation: start by adding links to the existing status views, and use the existing file preview for saved HTML. If two live views really show the same status, share that one small data helper or component. Nothing here justifies a shared dashboard framework or a broad refactor.

An environment is the place that owns the work.

It holds the running server, the files, provider credentials and conversation history. A laptop, a remote workstation and a build server can each be a separate environment. Your phone or browser is only the control panel: opening it there does not move the work onto that device.

  • Tunnel means the remote-access path through T3 Connect. Relay means the go-between that carries that connection. Neither is a second environment.
  • A direct connection uses the server's own address. SSH is a different, forwarded path with its own setup.

Manage routes in Settings → Environments on web, desktop or mobile. Open Routes to see the route In use, or choose Add route. A saved environment can have several routes. LastCode tries them in order, falls back when one fails, and can return to an earlier route once it works again. Pairing the same machine at another address adds a route, not another machine. The hosted HTTPS web client needs a secure route the browser can reach.

A device hub connects test devices

Open Settings → Devices → Device hosts. The environment's device hub finds simulators and emulators and streams them. By default they run beside its server. Under Device hosts, an SSH-connected machine can supply devices without owning your project or agent.

Example: Linux work, iOS testing

Your source and agent live on managed-server. An iOS simulator lives on a Mac called device-host. Add that Mac as an SSH device host to the Linux environment, and keep the Linux environment selected for agent work. Pick the Mac as the environment instead only if the project and provider themselves should run there.

  • SSH aliases and keys are looked up on the owning environment's server.
  • Test connection checks for tools without installing anything. The first device listing installs the pinned device tools.
  • Builds, app installs and a reachable development server still need setting up. A remote simulator cannot use another machine's localhost without a reachable address or port forwarding.

Can a child thread live somewhere else?

No. Grouped child threads and delegated subagents stay in their parent's environment. A child is grouped under its creator only when its environment and project match the parent's. The current create-threads operation makes threads in the caller's own project. Work on another machine is a separate thread owned by that environment, not a child that crosses environments.

The sidebar can group matching repositories from several environments. That changes what you see together, not who owns each thread. Auto balance can pick an environment for a new thread; existing threads stay where they started. On mobile you pick the environment yourself.

Reading another environment is possible; sending there is separate.

An agent's t3_thread_read first checks its own environment, then can ask your connected client to check its other authorized environment connections. It needs permission captured from that client and an eligible client that is still connected. It can also select an environmentId; later pages should use the environment returned by the first read. Use the returned thread link when sharing it.

If a destination is unavailable, that does not prove the thread is missing. A not-found result covers only the environments actually reached. Remote reading does not move the conversation or make t3_thread_send work across environments. To send there, use an agent or an authorized thread command on the owning environment.

A naming trap: a thread's Local workspace means the project's current checkout rather than a new worktree. It does not mean “on the device I am looking at.” Desktop's Local environment setting, by contrast, really is about the server on that desktop.

Recommendation: choose the environment by where the files, tools and credentials should live. Choose routes by how reliably you can reach it. Add a device host only when testing needs another machine's simulator or emulator.

A profile keeps a login. A capture keeps evidence.

The built-in Browser panel can sign in as different identities, capture a page, or record a short walkthrough. Desktop SnapShots capture another app into your draft. The names sound alike, but the jobs differ.

The short version: a profile is a reusable browser identity. A screenshot shows one moment. A recording shows what changed. An agent snapshot also describes the page's controls. None of these is a Git checkpoint.

Browser profiles: separate accounts without signing out

Go to Settings → Browser → Browser profiles → Add profile → Blank profile. Make one called Work and one called Personal, then pick a profile when you open a Browser tab. A tab keeps its profile for life; changing the default only affects new tabs.

  • A named desktop profile shares sign-ins across environments on that desktop. Work can keep the same account while you switch environments. Another desktop has separate login data. Select the same saved profile, not merely another profile with the same display name.
  • Default and Incognito stay environment-local. Default and custom profiles persist across restarts. Desktop Incognito lasts until that desktop process quits; environment-hosted Incognito is temporary. A temporary profile is a better choice for an isolated test.
  • You can create up to 24 custom profiles, with names up to 48 characters. Default and Incognito cannot be renamed or removed.
  • Clear cookies and cache also clears site storage, IndexedDB and service workers, so expect to sign in again. For a shared named desktop profile, that affects its tabs across environments on that desktop. Remove profile and data deletes the saved profile and its data.
  • Importing cookies copies them once. It does not keep syncing logins from another browser.

Pick the right kind of evidence

Capture How to make it Where it goes

Recordings: keep them short

  • A recording captures the preview browser tab only, with no audio.
  • Settings → Browser sets a maximum frame rate of 30 fps (the default) or 60 fps, and optional key and mouse overlays. Password fields never appear in the key overlay. Changes apply to new recordings.
  • The format is picked automatically: MP4 (H.264) when supported, otherwise WebM. Resolution follows the tab. There is no quality setting.
  • There is no fixed length limit, but agents can only transfer recordings up to 50 MiB. A short reproduction is easier to share than a long session.

Desktop SnapShots: show the agent what you see

  • Off by default. Available on macOS and Linux Wayland; X11 is not supported.
  • The default shortcut on macOS is both Shift keys together. On Linux, setup depends on the desktop.
  • macOS needs Screen Recording permission, plus Accessibility when Include app text is on.
  • The target draft is fixed when the capture starts, even if focus moves. With no thread open, the capture starts a draft in the current project. Captures not yet saved to a draft survive an app restart.
  • Sound, flash and animation only change the feedback, not the saved image.

There are no format, quality or size controls. Captures start as PNG. Attachments have a longest edge of at most 2000 pixels, so even an image smaller than 10 MiB may be resized. Extra compression is applied when needed to meet the 10 MiB attachment limit. Compressible sources up to 50 MiB can be processed; anything larger is rejected.

Agent snapshots

An agent snapshot helps the agent find buttons and understand the page, not just see pixels. Requested images are at most 1280 pixels wide, and page text is capped near 20,000 characters. Text-only is the default; includeImage: true adds the image. save: true saves a PNG and, without includeImage, returns its path or URL. Use both true to get the saved path and the usual page/image result.

Which apps can do this

The Browser panel can use a browser on your desktop or one running beside the environment server. Environment-hosted tabs stream to web, desktop and mobile; they do not require a desktop browser host. They support Default and Incognito, with agent-opened tabs using isolated Incognito unless Default is selected. Desktop-hosted tabs provide your named desktop profiles and saved sign-ins.

Choose Open in the environment's browser for pages beside its server, or Open on this computer for desktop browser access. This does not move the agent or its files. Browser setup and host availability still matter; support in the app does not guarantee the required browser is installed.

What retention deletes

Browser-artifact retention deletes expiring captures in its environment's artifact folder. It does not erase browser profiles, attached screenshots, recordings copied elsewhere, or Git checkpoints. Desktop camera and recording outputs stay on that desktop. When an agent stops a recording, it transfers or claims the result in the owning environment's attachments store, with a 50 MiB limit. Recordings are not all stored in the expiring browser-artifact folder. Desktop recording options do not necessarily apply to the environment-hosted recorder.

Recommendation: use persistent Work and Personal profiles for accounts, and Incognito for temporary tests. Use a screenshot for a layout problem and a short 30 fps recording for a sequence of steps. Use a SnapShot when the problem is in another desktop app. Before capture retention expires, keep lasting evidence as a deliberate attachment or saved file.
