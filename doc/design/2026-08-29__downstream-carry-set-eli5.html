LastCode release machinery · ELI5

Six commits on top of upstream, no matter how many PRs.

LastCode keeps its own changes on top of each T3 Code nightly as exactly six commits, one per named group. You still merge small, ordinary PRs. At the next publication, the automation folds every PR merged since the last one into the group each of its commits names, then replays just those six commits onto the new nightly.

PRs merged since the last checkpoint do not survive as separate commits. They are folded into the six group commits.

The Tiny Story

Imagine keeping your own changes to a recipe while the cookbook publisher releases a new edition every night.

Before

Replay every edit

The updater used to replay “add salt,” “use less salt,” “fix the salt test,” and every other edit, one by one, onto each new edition. By late August that was 117 commits per nightly.

Now

Six labelled sections

Each edit carries a label saying which of six sections it belongs to. Before each new edition, the updater rewrites the six sections to include the new edits, then pastes those six sections onto the new edition.

Unchanged

Small PRs, immutable tags

Work still lands as small reviewed PRs. Each published build is still an annotated lastcode/checkpoint/… or lastcode/revision/… tag that is never moved.

Why the fork needs it

The amount of LastCode behavior keeps growing. What the carry set removes is replaying every intermediate correction that led to it, and the repair PRs that replay used to produce.

The six groups, in their fixed order

The order lives in code, not just in the manifest. CARRY_REPLAY_GROUPS in scripts/lastcode-carry-replay.ts lists the six IDs, the manifest must repeat them in the same order, and a compiled chain with any other count or order is rejected. What belongs in each group is a written convention from the nightly workflow guide; the code only checks that every commit names one group.

1 · first

upstream-bugfixes

LastCode copies of fixes that exist, or were proposed, upstream. They go first because upstream may adopt, change or replace them.

2

tooling

Checkpointing, recovery orchestration and contributor automation.

3 · added after the proposal

build-ci

Dependency setup, CI, packaging and build verification.

4

resumable-actions

The core Action Resume behavior, without any sidebar presentation.

5

legacy-sidebar

Legacy sidebar behavior and its optional integrations, such as showing resumable action status. PR #671 later dropped the legacy sidebar mode to match upstream; that removal is itself a legacy-sidebar contribution.

6 · last

incubator

Everything else, and anything genuinely inseparable. Commits still have to name it: an untagged commit is refused.

Order matters; independence does not

A later group may build on an earlier one, so legacy-sidebar can show resumable-action status without the action feature depending on the sidebar. Only the complete six-commit chain is ever validated. No group, and no prefix of groups, has to build or pass tests on its own.

How a change gets its group

By a trailer on each commit in the PR, not by a list in the manifest.

Every commit names exactly one group

Before review, the author gives each commit in the PR one Carry-Group: trailer with one of the six IDs. A PR can span several groups by using several commits. PR #708, for example, has commits in build-ci, resumable-actions and incubator.

PR CI and the guarded merge both refuse a PR in which any commit has no group, has two, or is a merge commit.

Optional notes for future repairers

Commits can also carry Carry-Fix, Carry-Upstream, Carry-Observation, Carry-Evidence, Carry-Applies-To and Carry-Supersedes. They are copied into the group commit's metadata so whoever repairs a conflict later can see why a change exists and where it came from. Nothing requires them.

The manifest still has pullRequests lists for some groups and marks incubator as default. Carry replay reads neither. They are a frozen inventory from before carry replay was switched on, used only when checking a tag built by the old historical replay.

From PR to published build

The green steps are the compile checks. The amber step is where a genuinely new upstream conflict can stop the run.

What lastcode/main looks like

Between publications, lastcode/main is the six group commits plus ordinary squash commits on top. A publication folds those squashes away.

What “compile” makes, and what it promises

Six commits, rebuilt from deltas

Compiling starts from the previous six group commits and replays each new source commit's change into the group its trailer names, using an ordinary git rebase script. Each group ends as one commit titled carry(<group>): compile downstream group. Its message keeps one Carry-Contribution: line per source commit ever folded into it, with the commit hash, subject and notes, carried forward from generation to generation.

A group commit stays even when its changes cancel out to nothing, so the chain is always exactly six long.

The guarantee: same tree, same base

On the same upstream base, the six compiled commits must produce exactly the same files as the source they were compiled from: the PR's landing tree in CI, or lastcode/main at publication. If not, the compile fails.

One exception: when the previous build was never promoted, for example because a PR merged during its run, main does not contain that build. The trees cannot match, so the next publication compiles without this comparison. Checkpoint 3717 folded #508 to #510 that way.

This proves the regrouping lost nothing. It does not prove the result works on a newer nightly. That is what the replay and smoke gate are for.

Two edge cases the compiler handles Details

Moving a change earlier can conflict. Grouping replays changes in group order, not history order. A commit tagged legacy-sidebar that edits lines an incubator commit wrote earlier now replays before those lines exist. PR CI catches this, names the later-group commits that changed those lines, and suggests retagging or splitting the commit. PR #671 hit exactly this: deleting LegacySidebar.tsx had to become a separate incubator commit.

Deleting a file a later group introduced. If a commit deletes a file that a later group added, the compiler splits the deletion out and replays it with that later group, noting the split in the contribution's Carry-Observation and Carry-Supersedes.

What happens when a new nightly arrives

The checkpoint run does up to two things, in this order.

Step A · only if main moved

Fold new PRs into the groups

If lastcode/main is no longer exactly the last published build, the run compiles first. It takes the previous carry build's six commits, adds every squash merged since, and rebuilds the six commits on the old nightly. Each squash is checked against its retained source commits before they are used.

Example: the 4449 checkpoint folded 14 squashes, #671 to #688. The 4452 checkpoint had nothing new on main, so it skipped this step.

Step B · always

Replay six commits onto the nightly

The run rebases the six group commits onto the newest nightly that has no checkpoint yet, runs the smoke gate, and publishes an annotated checkpoint tag. If several nightlies are waiting, only the newest is checkpointed.

Then it moves lastcode/main to the six new commits. If someone merged a PR during the run, main is left alone and the next run picks it up. The published tag stays valid either way.

No new nightly? A revision does step A only.

When there is no new nightly but lastcode/main has new PRs, a run compiles them into the six groups on the current nightly and publishes a lastcode/revision/… tag, then moves main the same way. Merging a PR does not start a run by itself: lastcode:merge skips the checkpoint unless it is given --checkpoint, so folding waits for the next scheduled or requested run.

When something conflicts

Before merge: the PR author fixes it

A regrouping conflict in PR CI or the guarded merge blocks the merge. The author retags or splits commits and pushes again, because the owning PR is still open and can change.

At a checkpoint: a person or agent repairs it

A conflict while folding or replaying stops the run. It keeps the work on a sync/nightly/<nightly-tag> branch in a retained worktree, records the failure and sends a notification. A replay conflict also writes a conflict dossier into the worktree's git directory: the group that stopped, the contributions that touched each conflicted file, and the upstream commits that touched them.

Whoever maintains the fork repairs it there by following “Resuming a repaired checkpoint” in docs/lastcode/release.md. That procedure ends by selecting the repaired head with --select-recovery and --recovery-source, which folds repairs committed with their own Carry-Group trailers into their groups. The next run validates and tags the result, then promotes it, or defers promotion if main has moved.

Carry replay never uses git's remembered resolutions (rerere). Each carry conflict is resolved explicitly. For a fault in the carry machinery itself, a run can fall back to historical replay with --replay-mode historical and a required --rollback-reason, which is recorded on the published tag. It replays the last six group commits and then each new PR squash in turn, without regrouping, so it cannot get around a real conflict with upstream.

When upstream adopts a carried fix

Same change upstream: it quietly disappears

Replay is an ordinary three-way rebase. If the new nightly already contains the same change, that part of the group's diff has nothing left to add, and the group commit gets smaller. Nothing has to be deleted by hand.

Different change upstream: it becomes a repair

If upstream fixed it another way, the replay usually conflicts and goes through the repair path above. Retiring a carried fix on purpose is an ordinary PR that removes it, folded at the next publication like any other change.

No code removes a retired contribution's Carry-Contribution line. The metadata keeps listing a fix after upstream has absorbed its diff.

What changed from the proposal

Topic Proposal (2026-08-29) What shipped
Groups Five: Upstream bugfixes, Tooling, Resumable Actions, Legacy Sidebar, Incubator. Six. build-ci sits between tooling and resumable-actions.
Who assigns ownership A generated plan giving every downstream change one owner. The PR author, with one Carry-Group trailer per commit, enforced in CI and at merge.
Development history Merged PR commits stay on the branch for review. Squashes are folded away at each publication. Original commits survive in refs/lastcode/carry-sources/ and in the group commits' Carry-Contribution lines.
Upstream provenance Record the upstream PR for every Upstream bugfixes entry. Required only for the old manifest list. On a trailer it is optional: 122 of 252 upstream-bugfixes contributions on 2026-11-14 have no Carry-Upstream.
Exact-tree proof The ordered set reproduces the validated source tree. Shipped as the same-base compile check, run in PR CI, at merge and at publication, except a publication after a deferred promotion.
Patch budget Fail loudly above a chosen number of patches. Fixed at exactly six. Any other count or order is rejected.
Publishing after merge Merging must keep requesting publication automatically. Merging does not start a run unless --checkpoint is given.
Open PRs and promotion Open PRs keep lastcode/main still until the queue is empty. No open-PR check. Promotion takes a write lock on main and only moves it if main still equals the source that was compiled; otherwise it waits for a later run.
Incubator graduation Periodically move coherent clusters into named groups. Not built. Once work is folded into Incubator, nothing moves it out. A group is chosen only when a new commit is tagged.

Still unbuilt, or deliberately out of scope

  • Incubator graduation. Nothing moves folded contributions out of the catch-all group, which holds 1,015 of 2,256 contributions.
  • Retiring metadata. Contributions whose diffs upstream absorbed keep their metadata line indefinitely.
  • Upstream provenance on trailers. Nothing requires Carry-Upstream on upstream-bugfixes commits.
  • Compatibility with future nightlies. Out of scope by design. The compile check proves regrouping only; a real upstream incompatibility still stops a checkpoint and needs a repair.
  • Intermediate nightlies. When several nightlies are waiting, only the newest gets a checkpoint.

The words

Downstream carry set

Everything LastCode intentionally keeps on top of an upstream T3 Code nightly.

Group commit

One of the six carry(<group>): compile downstream group commits. The glossary calls these carry patches.

Contribution

One original source commit folded into a group commit, recorded as a Carry-Contribution line.

Compile

Rebuild the six group commits on the same nightly to include new source commits.

Replay

Rebase the six group commits onto a newer nightly.

Historical replay

Replay without regrouping: the last six group commits, then each new squash in turn. Kept as an explicit, recorded rollback.

History Why this page exists

In August 2026 the nightly process rebased LastCode's complete history onto each new T3 Code nightly, commit by commit. Failures produced repair PRs, which made later replays longer. The original version of this page proposed compiling merged history into a small, ordered set of named patches without adding manual steps to ordinary PR work.

That mechanism shipped and changed along the way: a sixth group, per-commit trailers instead of a generated ownership plan, a compile check in PR CI, and a bootstrap partition pinned in the manifest to start the first compact generation. The 2026-11-14 rewrite replaced the proposal text with the mechanism as built.
