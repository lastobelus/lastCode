LastCode design proposal · ELI5

Keep every idea. Stop replaying every draft.

Development can keep using small, ordinary pull requests. The nightly updater can carry their final combined result as a small set of named feature patches instead of replaying every implementation and repair commit forever.

Recommendation: compact the replayed history into a few coherent carry patches; do not replace normal PRs with permanent umbrella PRs.

Where This Is True Proposed · repository snapshot 2026-08-29

This page explains a proposal for LastCode's downstream nightly workflow. It is not yet implemented. The current checkpoint runner rebases commit history from lastcode/main, validates the result, and publishes immutable checkpoint or revision tags.

At this snapshot, the promoted downstream tree contains 117 commits after its upstream nightly base. Its final delta touches 468 files, while walking the commits touches file paths 1,082 times because later work revisits earlier files. Those measurements will change; the stable point is that development history and the final downstream delta are different things.

The proposal covers public repository structure and automation behavior. Concrete host identities, schedules, and deployment topology are outside this document. Re-check the nightly workflow and checkpoint source before treating this as current architecture.

The Tiny Story

Imagine maintaining a recipe while the cookbook publisher releases a new edition every night.

Today

Replay every edit

The updater replays “add salt,” “use less salt,” “fix the salt test,” and every other historical edit, even though only the final recipe matters.

Proposal

Carry the finished sections

Keep the edit history for review, but give the nightly updater a few named sections of the finished LastCode recipe: upstream bugfixes, tooling, resumable actions, legacy sidebar, and an incubator for everything that has not earned its own section yet.

Unchanged

Ideas still move immediately

Make an idea, merge its normal PR, and let automation publish it. Interactive and scheduled updates keep consuming the same ordered installable tags.

Why the pressure grows

The final downstream product naturally grows as LastCode gains capabilities. The avoidable growth is replaying every intermediate correction that led to that product.

What changes—and what does not

Concern Today Proposed
Development One-purpose PRs merge to lastcode/main. Unchanged. No umbrella selection step for the user.
Replay input Every retained implementation and repair commit. A small, generated carry set with named ownership and a fixed order.
Later fixes Each fix permanently adds another replay step. The next version of the owning carry patch absorbs the fix.
Updates Consumers select immutable checkpoint and revision tags. Unchanged. The tag contract and version ceiling remain.
Real incompatibility Conflict or smoke failure stops publication. Still stops publication. Compaction cannot erase semantic drift.

The words

Use these names so development workflow and release artifacts do not blur together.

Downstream carry set

Everything LastCode intentionally retains on top of an upstream T3 Code version.

Patch stack

A general Git term. In LastCode documentation, use downstream carry set for the durable fork delta.

Carry patch

One maintainable final-state unit inside the downstream carry set, with explicit ownership and a fixed place in the application order.

Start with the boundaries already visible

The current work already has feature families strong enough to justify separate carry patches. Upstream-facing fixes need their own volatile group, and an explicit catch-all prevents the first inventory from requiring premature taxonomy.

Carry patch · first

Upstream bugfixes

Imports of existing upstream PRs and LastCode copies of fixes also proposed upstream. Each fix keeps its upstream PR provenance because it may disappear, be partially replaced, or be solved differently upstream.

Carry patch

Tooling

Checkpointing, builds, update machinery, contributor automation, and their operational documentation. Its lifecycle and conflict surface are distinct from product features.

Carry patch

Resumable Actions

The essential action state, commands, composer controls, and resume behavior. The core remains useful without any legacy-sidebar presentation.

Carry patch

Legacy Sidebar

Legacy sidebar behavior and its optional integrations, including resumable-action visibility. Presentation belongs here because removing it does not remove the action capability itself.

Carry patch · last

Incubator

The starting bucket for everything else. Its contents do not pretend to form one feature; coherent clusters graduate into named patches when they accumulate enough ownership, maintenance weight, or replay risk.

Fixed order, not an independence gate

Apply Upstream bugfixes, Tooling, Resumable Actions, Legacy Sidebar, then Incubator. A later patch may rely on an earlier one, so Legacy Sidebar can show resumable-action status without making the action capability depend on the sidebar. Initially, only the complete ordered carry set needs to pass validation.

The Incubator is intentionally a catch-all. The guardrail is that its contents are not permanent by default: periodically graduate coherent clusters instead of letting one patch absorb every mature feature forever. Compaction changes the number of Git commits, not the amount of product behavior; migration collisions, changed upstream APIs, and conflicting edits still require strong validation.

Why not the two bigger reorganizations?

Permanent umbrella PRs

  • The diff, comments, and CI history grow without bound.
  • Stacked child PRs deepen the dependency graph we are trying to shrink.
  • They permanently pause lastcode/main promotion, although installable tags still publish.
  • A branch or generated artifact is a better durable container than an unfinished review.

A second fork

  • It does not reduce the final downstream delta or semantic conflicts.
  • It adds cross-fork mirroring, permissions, CI, and provenance failure modes.
  • If source and integration roles later need separation, refs in this fork are enough.

Safety rails before shipping it

  • Exact combined tree: prove the ordered carry set produces the same files and contents as the validated source tree.
  • Patch ownership: give every downstream change one owner, using Incubator until a more coherent group has earned its own patch.
  • Upstream provenance: record the source or paired upstream PR for every Upstream bugfixes entry and reevaluate it when upstream changes.
  • Incubator graduation: move a coherent cluster out when its ownership, maintenance weight, or replay risk justifies a named patch.
  • Fixed application order: store and replay one canonical ordered list; do not require every patch or prefix to pass independently.
  • Final-commit validation: run smoke and provenance checks against the commit that will actually be tagged.
  • Release-note continuity: preserve and test Source-Commit boundaries across the first compaction.
  • Bounded depth: fail loudly if an installable unexpectedly carries more than the chosen patch budget.
  • Immutable rollback: retain existing checkpoint and revision tags so the previous installable remains selectable.
  • No new human step: merging a PR must continue to request publication automatically.

One subtle point about open PRs

Open PRs do not prevent checkpoint or revision tags from being published, so they do not block updates. They only keep the moving lastcode/main branch stable until the PR queue is empty. The compact installable should preserve that behavior: publish the immutable tag now, promote the branch when safe.

The proposed decision

Approve automatic carry-set compaction as the next workflow change.

Keep normal PRs and the existing update experience. Begin with a small named carry set, ordered as Upstream bugfixes, Tooling, Resumable Actions, Legacy Sidebar, and Incubator; preserve provenance; fold fixes into their owning patch; and graduate coherent Incubator contents when they earn a dedicated group.

Prompt/context Why this page exists

The nightly process repeatedly rebases LastCode's complete retained history onto new T3 Code nightlies. Recent failures produced more repair PRs, which then enlarged later replays. The requested constraint was strict: ideas, ordinary PR work, ad hoc workstation updates, and scheduled server updates must not gain manual steps or become more brittle.

This explanation recommends compiling merged development history into a compact release artifact. Feedback on the first draft identified Tooling, Resumable Actions, and Legacy Sidebar as existing feature boundaries; resumable-action sidebar visibility belongs to Legacy Sidebar because it is optional presentation. Further feedback added a changeable Upstream bugfixes group with PR provenance and an Incubator catch-all for changes that have not yet earned a dedicated group. The proposal does not prescribe private deployment topology or claim that compaction solves genuine upstream incompatibilities.
