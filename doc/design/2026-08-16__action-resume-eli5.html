LastCode issue #13 · ELI5 architecture

The same thread, with a doorbell

T3 Code already knows which conversation an agent belongs to, can run saved Actions in terminals, can observe terminal exits, and can start another agent turn. Today those pieces did not talk to one another. The issue #13 branch adds a small, explicit bridge between them.

It resumes the same existing thread. It never creates a new thread.
Existing T3 Code piece LastCode addition in this branch Recovery or boundary case
Where this is trueImplemented in worktree · not shipped

This page compares ordinary T3 Code with the implemented first slice of lastobelus/lastCode#13, as inspected on 2026-08-17. Green pieces predate the feature. Orange pieces now exist in this worktree but have not been committed, reviewed, or shipped.

Scope: Codex only; web and desktop only; one locally opted-in Action at a time per thread; one durable, idempotent follow-up in the originating thread. There are no timeouts. Mobile UI, other providers, general scheduling, and arbitrary commands remain outside this first slice.

The tiny story

1

T3 Code already has the parts

A thread, an agent session, saved Actions, managed terminals, exit events, and a normal way to start another turn.

2

One connection is missing

A terminal finishing does not tell the originating agent thread, “your requested work is ready.”

3

We added a doorbell

An explicit agent-only Action invocation arms one wake. Completion plus an idle thread rings it exactly once.

Vocabulary without the architecture accent

These words are ordinary product concepts with codebase-specific names.

ProjectA workspace or repository that LastCode knows about.
ThreadOne durable conversation and its work history. Think “chat plus workbench.”
TurnOne round inside a thread: input goes in, the agent works, a response comes back.
ProviderThe agent engine doing the work, such as Codex or Claude.
Provider sessionThe live connection between one thread and its agent engine.
ActionA saved project command such as “Quick CI.” The code still calls these project scripts.
TerminalA shell managed by T3 Code and associated with a thread.
ActivityA truthful system log row in the thread, distinct from a human chat message.
MCP toolA button/API exposed to the agent. Calling it carries authenticated thread identity.
CommandA typed request to change LastCode state.
EventA recorded fact that a typed command was accepted.
ReactorA background worker that performs side effects after an event, such as calling Codex.

Diagram 1 · The container model

A project has multiple threads. A thread has multiple turns and may own terminals. An Action belongs to the project, but it runs in a thread’s terminal.

The key distinction A new turn is just the next round inside the same conversation. A new thread would be a separate conversation. Issue #13 adds the former, never the latter.

The comparison in one table

Question Ordinary Action today Resumable Action in this branch
Who starts it? A person clicks or uses a shortcut. The agent explicitly calls the tool—whether a user prompt or a skill told it to.
Where does it run? A terminal associated with the active thread. A dedicated terminal associated with the originating thread.
Does configuration opt in? No resume capability exists. Yes. Local per-Action permission, default off.
What happens on exit? The terminal shows exit state. LastCode records typed lifecycle metadata and keeps the transcript in that terminal.
Does the agent wait? It must poll, sleep, or rely on the user. No polling turns. LastCode waits for terminal completion and thread idleness.
What conversation changes? Nothing automatically. One new turn begins inside the same thread.
Is there a fake user message? Not applicable. No. The follow-up is stored and rendered as a system-authored message.
Where is output? Terminal history. The dedicated terminal transcript. Raw output is not copied into the automatic prompt.
How does the user see it? The terminal drawer. A yellow Waiting indicator with elapsed time, Open Terminal, and Cancel Action.
Can it time out? The command runs until it exits or is stopped. No timeout. The user can cancel it explicitly.

The implemented bridge

Orange is the new glue. Green is existing T3 Code machinery we reuse.

Diagram 4 · End-to-end implemented flow

The current agent turn ends before the Action does. The result starts the next turn only after the same thread is idle.

How much is reused?

Diagram 5 · Mostly existing railway, one new junction

The feature does not replace Action execution or provider turns. It joins their existing tracks.

Reuse

Project Action model. T3 Code already persists named commands and exposes them in the UI. We add one local boolean; we do not invent a task database.

Reuse

MCP invocation identity. Calls already carry environment, thread, provider-session, and provider-instance identity. The agent does not get to nominate some unrelated thread.

Reuse

Terminal manager. It already opens thread terminals and publishes output, exit, close, error, and activity events.

Reuse

Thread and provider lifecycle. LastCode already knows whether the thread’s current turn is running or idle and already knows how to ask Codex for another turn.

Add

One-shot coordinator. A durable activity row plus a small in-memory projection correlate run ID, Action, thread, terminal result, delivery, and restart recovery. It is not a general scheduler.

Add

Terminal-only output boundary. The existing terminal transcript remains the artifact. The automatic follow-up contains only LastCode-authored status and the terminal ID—never raw command output.

Add

System turn seam. The internal turn command now permits a server-originated system message, while the client command remains user-only. The ordinary provider reactor does the rest.

Add

User controls. Waiting appears in the sidebar with elapsed time, terminal access, and cancellation. Archive and terminal close cancel; quit reports how many running Actions it will cancel.

The trust boundary

How the ordinary turn command is reused without lying

Existing behavior

thread.turn.start

Client-originated starts still record a user message, then ask the provider reactor to find that message and send its text to the provider.

Narrow addition

A system role inside the same command

The internal command accepts a server-originated system message; the client-facing schema remains user-only. The same projector and provider reactor then run the turn. No human message is manufactured.

This is the part we were discussing. “Machine turn” does not mean “new thread.” It means “the next agent round was initiated by LastCode because an explicitly armed Action finished.”

What does not happen

Thread and agent boundaries

  • No new thread is created.
  • No unrelated thread can be selected by the tool input.
  • No ordinary terminal exit wakes an agent.
  • No UI Action click quietly gains automation powers.

Scope and trust boundaries

  • No checked-in t3.json can grant permission.
  • No terminal output is injected into the automatic prompt.
  • No polling handle or wait tool is introduced.
  • No general task scheduler is built.

Failure and recovery, plainly

Situation Proposed behavior Why
Action is not opted in Tool rejects before launch. Fail closed.
Ordinary Action click Runs normally; no wake. Eligibility is not arming.
Action finishes before the turn ends Store result; wait for idle event. Prevents the tool call from steering its own turn.
Thread becomes idle before Action finishes Wait for terminal result. Both signals are required.
Duplicate terminal/session events One accepted command consumes the wake. Exactly one follow-up.
User closes the dedicated terminal Record user cancellation and send one automated cancellation follow-up. Closing the work surface is an explicit cancel.
User archives the thread Cancel the Action, close its terminal, and dispose the wake. An archived thread must not wake later.
User quits LastCode Warn with the running count; confirmed quit records shutdown cancellation and does not nag after restart. Intentional shutdown is different from a lost process.
LastCode stops unexpectedly Mark the process lost, rerun nothing, wake nobody, and show one aggregate Review notice. “Resume agent” sends only the interruption follow-up. Recovery is explicit and cannot duplicate the command.
Thread is permanently deleted Clear the projected Action state with ordinary thread cleanup. No orphaned UI state.

Settled first-slice choices

Implemented

The follow-up is visibly machine-originated

A narrow system-message seam reuses thread.turn.start. The timeline labels it “Automated follow-up,” while ordinary client sends remain user-only.

Implemented

No timeouts; explicit cancellation and recovery

Actions may run indefinitely. Terminal close and archive cancel them. Quit warns. Unexpected restart never replays the command and requires the user to choose “Resume agent.”

Prompt/contextWhy this page exists

The user asked for an ELI5 with ample diagrams after architecture terms made it sound as though #13 might create new threads. This page therefore leads with the product mental model, compares ordinary conversation and Action flows separately, and marks every added piece. Constraints carried forward: agent invocation from either direct prompting or skill guidance, no polling turns or timeouts, explicit local opt-in, truthful system-authored follow-up, terminal-only raw output, visible Waiting and cancel controls, restart-safe recovery, and no general orchestration framework.
